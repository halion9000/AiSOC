# Making row-level security fail-closed: what was measured, what breaks, and the order to do it in

Status: **steps 1 and 2 below are done (for the two cross-tenant readers found so far) and change no behaviour; steps 3 to 5 are a plan and have not been started.** Nothing in steps 3 to 5 has been deployed. Every number below was measured on a scratch PostgreSQL as the restricted role `aisoc_app`, using the repository's own isolation flows (`python -m app.scripts.tenant_flows run`, 435 steps over two tenants), unless it says otherwise.

## Where things stand

- **77 policies are fail-open.** Their `USING` expression ends in `OR current_tenant_id() IS NULL`, so a session that never set a tenant sees every row. Three shapes: 63 of `tenant_id = current_tenant_id() OR current_tenant_id() IS NULL`; 12 that also allow `OR tenant_id IS NULL` (shared rows); 2 that go through a `role_id` subquery.
- **One policy is already fail-closed** (it coalesces an unset tenant to the all-zero UUID and has a `WITH CHECK`). It is the in-house template for the change.
- 33 RLS tables use `FORCE ROW LEVEL SECURITY`, 45 do not (so the owner bypasses them).
- **RLS only protects a connection that is not a superuser.** The default compose connects every service as the bootstrap superuser `aisoc`, which bypasses all of it. `docker-compose.rls.yml` moves only `actions` and `agents` to `aisoc_app`; it says the API "is deliberately NOT switched yet", but the API can already be run that way (`DATABASE_URL` = `aisoc_app`, `MIGRATION_DATABASE_URL` = the owner), which is how the flows below were run. Making the policies fail-closed changes nothing for a deployment that connects as the superuser.
- Of the other services' tables, only `response_actions` is in the API's RLS-covered schema (and `actions` already runs as `aisoc_app`). The tables of `osquery-tls`, `honeytokens`, `ueba` and `purple-team` do not exist in that schema.

## What was measured

| Experiment | Result |
| --- | --- |
| Flip all 77 policies to fail-closed, nothing else | **251 of 404** flow steps fail. Writes fail with `new row violates row-level security policy` (a 503); reads return empty lists with a 200. |
| Same, plus a central hook (below) | **0 of 435** fail |
| The hook alone, on today's policies | **0 of 435** fail |

**Why the first one breaks.** A plain `get_db` session never sets a tenant. `get_tenant_db` sets one with `SET LOCAL`, which lasts for the first transaction only: after a handler's `commit()` the next statement runs with no tenant (for example `Could not refresh instance` after a create).

**The hook.** `get_current_user` and `get_tenant_db` tag the session with the caller's tenant (`session.info`), and a SQLAlchemy `after_begin` listener re-applies `set_config('app.current_tenant_id', …, true)` at the start of **every** transaction, so it survives a mid-request commit.

## The finding that stops the hook from going out alone

The flows have two ordinary tenants. They have no managed (parent/child) tenant, so they cannot see **cross-tenant reads on a `get_db` session, which depend on the fail-open behaviour**.

`app/services/mssp_rule_resolver.py` builds a managed tenant's effective rules, including rules owned by the **parent** and assigned through packs. It is reached from at least `POST /rules/hunt` (`detection_rules.hunt`, which uses `get_db`) and `GET /mssp/children/{id}/effective-rules` (`get_db`); the sibling `GET /mssp/children/{id}/effective-rules/count` was not examined. Measured by creating a parent, a child, a parent-owned rule, a pack and an assignment, then calling the real resolver as `aisoc_app`:

| Session state | Effective rules returned for the child |
| --- | --- |
| No tenant set (what a `get_db` session is today) | the parent's pack rule |
| Tenant set to the **child** (what the hook does when a child calls `/rules/hunt`) | **nothing** |
| Tenant set to the **parent** (what the hook does for the MSSP route) | the pack rule (the child's own rules would be hidden) |

So the hook alone would make a managed tenant's hunt **silently run without the rules its MSSP parent assigned**. The same applies to fail-closed policies.

Not affected: the tables the MSSP overview routes aggregate across children (`mssp_tenant_metrics`, `mssp_rule_overrides`, `tenants`) have **no RLS**.

**A second cross-tenant reader, found by reading and by inspecting the policies (not run end to end): `app/services/view_as.py`, the "view another tenant" feature.**

- `viewable_access` (called from the `GET /tenants` route that lists the tenants a person may view) reads the person's rows in `tenant_access_grants`, which has RLS (`tenant_id = current_tenant_id() OR current_tenant_id() IS NULL`). Under a session tagged with the person's home tenant it would see only the grants whose `tenant_id` is the home tenant.
- `record_view` (called from `get_current_user` itself, `deps.py:278`) reads the **target** tenant's `audit_log` rows to avoid duplicate view events, and then **writes** the `tenant:viewed` event with `tenant_id = target`. `audit_log` is `FORCE` RLS with the same shape of policy. **Neither policy has a `WITH CHECK`** (checked in `pg_policies`), so PostgreSQL applies the `USING` expression to writes as well: a session tagged with the home tenant could not insert a row for the target. The code deliberately refuses to serve a view it cannot record ("a view that cannot be recorded is not served"), so **cross-tenant viewing would stop working altogether**, not just return less.
- So it needs both the explicit read block **and** an "act as this tenant for this write" for the audit insert, and it must be resolved **before** the hook tags the session (the order inside `get_current_user` matters, and the effective tenant after view-as is the viewed one). It also touches the audit log's integrity (hash chain, `FORCE` RLS), which deserves care and a review of its own.
- **Done, with evidence.** Run on a real Postgres as `aisoc_app` with the real `emit_audit` and `record_view`: with no tenant set the event is written and chained; with the session tagged with the viewer's home tenant **the insert is rejected** (`new row violates row-level security policy`) and **the chain-head read returns `None`**, which reads as "genesis" and would silently **fork the target's audit hash chain** if only the insert were let through; acting as the target, both work and the chain is correct. So the read of the chain head and the insert must share one scope.
- **The second block, `acting_as_tenant(session, tenant_id)`** (`app/db/rls_scope.py`), sets the tenant setting **and** the session tag to the target for the block and restores both. Both blocks flush pending writes **before** the scope changes and again **before** it is restored, because `session.add()` only queues a write that SQLAlchemy sends later: without that, a write made for the target could be sent under the restored scope and rejected. They are no-ops unless the session is clearly bound to PostgreSQL.
- **Applied:** `record_view` and `record_act_as` (which both read the target's chain head, add the event and **commit inside the function**, so the commit is inside the scope) run in `acting_as_tenant(target)`; `granted_tenant_ids`, `access_grants` and `viewable_access` run in `cross_tenant_reads`. The change to `view_as.py` is purely additive (40 lines, none deleted).
- **Tested:** `tests/test_cross_tenant_reads.py` (unit, with a recording fake session) and `tests/test_view_as_audit_postgres.py` (opt-in, real Postgres as `aisoc_app`: it checks the hash chain, not just that a row exists, has a negative control that the undecorated function fails under a home-tagged session, and a dedupe check). That file **cannot clean up** after itself: `audit_log` is immutable (a trigger blocks `DELETE` and `UPDATE`, which also blocks the cascade from deleting a tenant), so it must be pointed at a disposable database. `record_act_as`, `granted_tenant_ids` and `viewable_access` are covered by the unit tests only.
- **Still true:** behaviour today is unchanged (a plain `get_db` session has no tenant set; `record_view` and `record_act_as` already filter by the target explicitly). The effective-tenant order inside `get_current_user` still has to be checked when the hook is added (step 3), because `record_view` is called from inside it.

**A third cross-tenant reader and writer, found by a static scan: tenant access management (`app/api/v1/endpoints/tenants.py`: `list_tenant_access`, `grant_tenant_access`, `revoke_tenant_access`).** `may_manage_access` lets a **platform holder manage any tenant** and an **MSP parent manage its children**, so these routes read and write the **target** tenant's `tenant_access_grants` (an RLS table) and write an audit event into the **target's** log, from a session whose tenant is the caller's. The same two failures as `view_as`: the grant and audit inserts are rejected under a session tagged with the caller's home tenant (no `WITH CHECK`), and the reads of the target's grants see nothing. The grantee lookup is **not** affected: `users` has no RLS (the RLS tables among those involved are `audit_log`, `roles`, `tenant_access_grants` and `user_roles`).

- **The scan** (heuristic, so it produces candidates to read, not findings): every endpoint function that takes a tenant-like parameter (`tenant_id`, `child_id`, `parent_id`, …), uses a plain session rather than a tenant-scoped one, and references any of the 62 RLS-covered ORM models. 10 candidates; read by hand: `easm` checks `tenant_id != current_user.tenant_id` and answers 403 (own tenant only); `identity_graph._require_own_nodes` and `rbac._get_role_or_404` are own-tenant by construction; `effective_permissions._maybe_live_snapshot` and `federated._fetch_target_connectors` filter by an id that most plausibly is the caller's, **not verified**; `llm_status.tenant_llm_status` is a helper whose callers' tenant was **not determined**. The scan does **not** cover services called from several handlers that take no tenant-like parameter, or code that gets another tenant's id some other way, so it is a lower bound.
- **Fixed with `acting_as_argument("tenant_id")`** (`app/db/rls_scope.py`), a decorator that runs a route in `acting_as_tenant(<the tenant its path names>)`. It is applied after FastAPI has authenticated the caller and checked the route's permission; the handler's own `may_manage_access` check runs inside the block, and nothing read before that check is covered by a tenant policy (`tenants` has none). `tenants.py` changed by 7 inserted lines and none deleted, and **the OpenAPI of the three routes is byte-identical** before and after (the decorator keeps the signature), which I checked rather than assumed.
- **A weakness found by my own test and corrected:** the blocks first sent **no** restore statement when the body raised, on the theory that a failed transaction is rolled back anyway. But a 404 raised by business logic is not a failed transaction, and a caller that handled it and carried on would have been left scoped to the target. Now, after an **ordinary error**, the setting is put back **best-effort** (a failure is swallowed so the original error is the one that propagates; pending writes are never flushed after an error); after a **successful** block a failed restore propagates; after **cancellation** (a `BaseException`) nothing is sent, because awaiting in `finally` is not safe.
- **Transaction-local scope, and why the Postgres test emulates the hook:** the tenant setting lasts for one transaction, and these handlers commit (and, on a race, roll back and re-query). The scope carries into the next transaction **only through the step-3 hook** re-applying the session's tag, so `tests/test_tenant_access_postgres.py` registers an `after_begin` listener that does what the hook will, and runs every route in both session states. Without the hook (today) it makes no difference, because the policies are fail-open.
- **Tested:** unit tests (the decorator; each of the three routes runs its work under the path tenant's scope; a completeness guard that every `{tenant_id}/access` route is decorated) and 9 real-Postgres tests with a negative control (the undecorated grant is rejected under a home-tagged session) and audit-chain checks, including a level change that writes a second event chained to the first. 5 of 5 deliberate breakages caught. That file also **cannot clean up** (`audit_log` is immutable).

Checked and **not** affected: `app/api/v1/endpoints/nl_query.py` reads only `tenants` (no RLS) to validate which tenants a query may span; the cross-tenant query itself runs against the lake, not through these policies.

Still unreviewed: any other reader of another tenant's RLS-covered rows on a `get_db` session. Two were found by looking at the two obvious candidates; there may be more, which is the reason for the tripwire-first order below.

**A correction to my own prediction.** I expected platform built-in rules (`tenant_id IS NULL AND is_builtin`) to disappear too. They cannot: `detection_rules.tenant_id` is `NOT NULL`, so that layer of the resolver matches nothing.

## Code paths with no signed-in user (they need an explicit mechanism)

`audit_middleware` (writes from its own session; the tenant is known from the token), the `oauth_refresh` and `weekly_digest` workers (cross-tenant sweeps), login, SSO, public signup and webhook ingestion. The hunt scheduler was the one that used `SET LOCAL row_security = off`, which fails for a non-superuser; that is fixed (`17c6f71c`), but the sweep still relies on a tenant-less session seeing every tenant, which fail-closed policies would remove.

## Proposed order

1. **A tripwire first. DONE, with a caveat.** `tests/test_mssp_resolver_cross_tenant_postgres.py` builds a real parent, child, parent-owned rule, pack and assignment, and runs the real resolver **as `aisoc_app`** with no tenant set, with the child's tenant set and with the parent's, plus a negative control that proves the RLS filter really applies to that role. Reintroducing the original bug (the resolver without the block below) makes it fail. It is an opt-in test in the suite's existing style (`AISOC_TEST_PG_URL` and `AISOC_TEST_PG_APP_URL`, a disposable migrated database) and is **skipped in CI, which does not set them**: someone has to wire it into a job with a Postgres service (`integration.yml` has them) before it protects anything automatically. It lives at the resolver, not in the isolation flows, because the flows act as ordinary tenant admins over HTTP and cannot create a parent/child relationship.
2. **An explicit, narrow cross-tenant read mechanism. DONE for the one reader found.** `cross_tenant_reads(session)` (in `app/db/rls_scope.py`, re-exported from `app/db/rls.py`) clears the tenant setting for the length of a block (an empty string is the same as unset for `current_tenant_id()`), untags a session tagged by the step 3 hook so the hook cannot re-apply it, and puts back the setting that was in force. `resolve_effective_rules` now runs inside it (and `count_effective_rules`, which calls it). Verified on a real Postgres: the child's effective rules now include the parent's pack rule in all three session states, where the child-tagged state returned nothing. **Today it changes nothing** for the callers (both use a plain `get_db` session with no tenant set). It lifts the policy's filter, it does not replace it: the resolver filters by tenant and parent explicitly. With fail-closed policies it will need a granted bypass (step 4). `view_as.py` (below) now uses it for its grant reads, and its audit write uses the second block, `acting_as_tenant`. **Only the readers the scan below found have been reviewed.**
3. **The hook, behind a flag that defaults off**, then on, verified by the flows including step 1.
4. **Policies to fail-closed**, using the existing fail-closed policy as the template, with a bypass for workers and platform operations (step 2).
5. **Make the API connect as `aisoc_app` by default** (the overlay's stated direction). Until then, none of this protects the default deployment.

Each step is independently reversible; steps 1 and 2 change no behaviour. **Steps 3 to 5 are not started: they need a decision, because they touch login, the workers and every deployment's database role.**
